- (a) bulk focus-node injection: over-cap `gl_alloc` -> null (typed, no trap);
  hostile-host len misreport -> typed `ResourceLimit` `request_bytes`;
  gl_call(0,0) -> typed `Unsupported` "request buffer missing";
  never-frees host saturates at 255-256 MiB -> null alloc (no UB);
  one free -> exactly one alloc re-admitted; drain -> full budget, evals OK.
- (b) compute-explosive: N3 string-doubling refuses typed `ResourceLimit`,
  bounded (<60s), instance survives and still evaluates; depth-200 JSON body
  -> typed `json_depth` (max 64) refusal.
- (c) accumulation: 1200 leaked evals on one instance, memory plateau within
  8 pages (512 KiB) per 600-eval sweep, all typed ok.
- Survival: saturated instance dropped; FRESH instance (Smalt.Wasm.Pool
  respawn analog) admits a valid capabilities request immediately; host
  process never UBs.

## Findings worth the coordinator's attention

1. The typed `request_bytes` refusal is UNREACHABLE for an honest host: the
   module refuses the allocation itself at gl_alloc (null). Only a hostile
   host misreporting len reaches the typed refusal. The smalt worker
   (wasmtime --max-memory 67108864) is the real hard wall — see boundary map.
2. Off-by-one: never-frees saturates at 255x1MiB (267,386,880 B) on a fresh
   private instance, not 268,435,456 — one MiB short of the documented
   MAX_OUTSTANDING_BYTES. Court asserts the band [255, 256] MiB. Typed as
   SUSPECT off-by-one in ffi.rs reserve accounting (cosmetic; refusal
   fail-closed either way). If a lane pins it to exactly 256 later, tighten
   the court's band to equality.
